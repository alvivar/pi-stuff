pi-link · how it works

Several Pi terminals,
one conversation between them.

A Pi extension that lets terminals on the same machine find each other, send each other work, see who is busy, and ask each other to compact. This page follows the real code, one piece at a time.

01

The pieces

Three files do the work, plus Pi itself. The extension is the core: every terminal loads the same index.ts and ends up either hosting the network or joining it.

index.tsThe extension

Networking, routing, inbox, status, tools and slash commands, all in one file that Pi loads into each terminal.

bin/pi-link.mjsThe CLI

Starts Pi with a named, resumable session, lists sessions, and asks the running hub who is connected.

skills/pi-link-tools/SKILL.mdThe skill

Teaches the model how the three tools really behave: delivery, snapshots, callbacks, groups.

wsOne dependency

Plain WebSockets. Everything else is Node and the Pi extension API.

02

A star on localhost

The network is hub-and-spoke. One terminal hosts a WebSocket server on 127.0.0.1:9900; every other terminal connects to it as a client. Clients never talk to each other directly: every message goes through the hub.

Being on one machine is a design decision, not an accident: no authentication, no network exposure, and working directories that mean something to every participant.

03

Finding a hub: try, then become

There is no leader election. On startup (--link, or the pi-link launcher) and on /link-connect, initialize() runs one simple fallback. Whoever binds the port is the hub.

Only one attempt is ever in flight. A startup connect, a retry and a manual /link-connect all join the same attempt instead of opening a second socket, and the attempt record itself is the ownership token: callbacks from a cancelled or superseded transport are inert.

04

Joining, and who you are

A client's first frame is register, carrying the name it wants, its cwd and its context. The hub answers with welcome, the assigned name plus a snapshot of everyone already connected, then tells the others with terminal_joined.

Names

The requested name is resolved once per session, in this order:

--link-name› PI_LINK_NAME › saved via /link-name› session name › random t-a1b2

The hub keeps names unique with uniqueName(): a second builder becomes builder-2. The name you asked for is what gets saved and requested again on reconnect, not the suffixed one.

Groups

A name like archon@pi-link belongs to group pi-link, the text after the first @. The hub routes every group over the same connections, but routeMessage() treats a target in another group as not found, and link_list only shows your own. Suffixes touch the local part only: archon-2@pi-link. It isolates attention, not security.

06

A message's journey

When a model calls link_send, the text travels as a chat frame through the hub to the target, where it does not go straight into the model. It lands in an inbox first.

Two properties follow from the code:

The window is fixed, not sliding. scheduleFlush() only arms a timer when none is pending, so later arrivals join the window instead of pushing it back. A flood cannot starve delivery.

Success means "accepted", not "read". On a client, routeMessage() returns true as soon as the frame is on its way to the hub. There are no receipts; a reply is just another link_send from the other side.

07

Status and context: pushed, not polled

Each terminal tells the others what it is doing. Pi's lifecycle events mutate a few flags, one function turns them into a single status, and it is broadcast only when what a peer would see actually changed.

Why compacting comes first. Reporting compacting and holding delivery are the same condition, compactionGated(), so a peer's view and the inbox cannot drift apart.

Why context rides along. The context snapshot is read at push time, so every status change carries a fresh figure. The forced pushes cover changes that alter usage without changing status: after a compaction, a model switch (the window changes, so the percentage does too) and a move to another branch of the session tree.

Parallel tools don't churn. The displayed tool is the first still-running call; a second starting behind it is silent.

Peers only ever see the last published snapshot. link_list computes your own entry live; everyone else's is what they last pushed.
08

Remote compaction

link_compact asks another terminal to run the same operation as /compact and waits for the answer, at most five minutes. The target decides.

Why hold the inbox at all. A message delivered while the context is being rebuilt would be reasoned about against context that is about to disappear. Automatic compaction is left alone: it runs inside an agent run, where Pi already queues steered messages.

Timeouts bound waiting, nothing else. A requester that gives up does not abort the target; the compaction runs to its own end. A local gate left up by a failure is released by the next run, a later compaction, or a 300 s backstop.

09

When the hub dies

Clients see their socket close, go disconnected, and schedule a reconnect after a random 2–5 seconds. Then they run the same initialize() as at startup. The first to retry finds no hub, binds the port and becomes one; the rest join it.

Nothing is handed over. Every terminal drops the snapshots it held about others (names, statuses, cwds, context) and keeps its own state, inbox included. The new roster is rebuilt from fresh register frames.

10

The CLI, outside the network

bin/pi-link.mjs never joins the link. It does three jobs around it:

pi-link builderLaunch by name

Resumes the session named builder in this cwd (or creates it) and starts pi --link, handing the name over through PI_LINK_NAME, which the extension reads once and deletes.

pi-link --listFind sessions

Scans Pi's session directory with the same lookup rules Pi uses, so it sees what Pi sees.

pi-link --status [--json]Ask the hub

Plain HTTP GET /status on the hub's port. The hub owns the HTTP server its WebSocket server rides on, which is what makes this possible.
