FIELD GUIDE / RESIDENT PI
Resident agents · Durable sessions

The terminal
closes.
The agent stays.

Create a named Pi agent. Give it work. Keep the run ID. Come back later. Its process lives outside your terminal; its conversation survives power-off.

ONE NAME. ONE RUNNER. ONE SESSION.No central daemon · No build · Pi SDK
01 THE IDEA

Not a disposable task.
An agent to come back to.

Finishing a prompt does not end the process. With no more work active, the agent returns to idle and waits. Turning it off does not erase its history either: when it wakes, it opens the same session.

A / IDENTITY

Create ≠ send work

spawn creates an identity without sending a prompt. send only works with existing names. A typo never silently creates another agent.

B / RESIDENCE

Lives outside your shell

The process is launched with detached: true, ignored stdio and unref(). It is still there when the CLI exits.

C / CONTINUITY

Power off, not memory loss

stop aborts and powers off the runner. Manifest, log and session remain. There is no destructive rm command.

03 THE CYCLE

The work ends.
The identity continues.

Five states describe what we observe: three while powered on, two while off. There is no stored status field to become stale after a crash.

idleon · waiting
⇄
runningon · working
send → work   /   work done → idle
compactingon · explicit context summary
idle → compact → idle
stoppedexplicitly powered off
/
failedcrash · fatal error
↑ start, send or compact wake the same identity

A failed run is not a failed agent. A reported turn error writes run_failed and normally leaves the runner on. A thrown prompt exception shuts it down. Failed explicit compaction also leaves it on.

State comes from the live pipe. Without it, the last complete log event determines stopped or failed; any other ending means failed. The compacting state tracks explicit compaction, not automatic SDK compaction.

04 ONE PROMPT

“Received” does not mean
“done”.

send prints a prompt ID and exits after acceptance. The runner works independently. Use that ID to wait for the outcome, even from a later terminal.

01 / DELIVER

Find the identity

Reads the manifest. If the runner is off, wakes it and opens the saved session.

02 / CONFIRM

Queue and reply

The runner logs queued with a new ID. The pipe returns {"ok":true,"id":"…"}; the CLI prints only the ID.

03 / EXECUTE

One run at a time

A promise chain serializes pipe prompts. After the SDK is idle, run marks the start. Turns and text carry the same ID.

04 / OBSERVE

Record the outcome

Text is logged at turn end. After the SDK settles, done or run_failed ends the run. There is no idle log event.

Illustrative example · delivery now, outcome later
$ pi-dock send atlas "Remember the token ALPHA-31"
p4a31b6c902ef                    ← acceptance, not the reply

$ pi-dock wait atlas p4a31b6c902ef
I will remember ALPHA-31.

# Or send and wait together:
$ pi-dock send atlas --wait "What token did I give you?"
p71c204a93bef                    ← ID on stderr
ALPHA-31                        ← final-turn text on stdout

Wait observes; it does not resend. It reads the correlated log and reports success or failure without waking or retrying the agent. Only the last turn's text is returned, not all turns joined together. A successful run with an empty final turn prints nothing.

05 WHAT LASTS

Three conceptual files.
Three responsibilities.

The name points to a configuration and to a standard Pi session. The log makes the agent easy to observe, but it does not replace its full conversation.

  • model · thinking

~/.pi/dock/atlas.log

NDJSON events appended in order. Each start records its PID; turns contribute text.

  • spawned · queued · run
  • turn · text · done · run_failed
  • compacted · compact_failed · dropped
  • stopped · failed

Pi session .jsonl

Path given by sessionFile

The persistent conversation managed by the SDK. It uses Pi’s standard session format and does not necessarily live in the dock directory.

  • Create → SessionManager.create(cwd)
  • Wake → SessionManager.open(…)
  • Power off → keep the session

Identity is not overwritten under contention. Creation publishes the manifest with an exclusive hard link. The CLI verifies that the PID of the responding runner is its own child's. set replaces the manifest atomically, only after confirming the pipe is absent.

06 THE BOUNDARY

Resident does not mean
restricted.

There is no pi-dock turn, time or spending cap. Work can continue until you stop the agent or it crashes—including work started by extensions while no pipe prompt is active.

You own the off switch.

∞

Closing a shell is not cancellation. stop aborts active work and powers off. Queued prompts are not resumed on wake: dropped lists their IDs. The conversation survives; the in-memory queue does not.

An ID marks a run, not every input.

extension work
no ID→SDK idle→pipe run
with ID

Existing idle extension work settles before the pipe run starts. Work that joins while that run is active can share its attribution until the SDK is idle again.

The dock log is an observation stream, not a complete input audit. The SDK session holds the conversation.

Headless does not mean isolated.

The runner loads project resources and extensions without Pi's interactive trust dialog. Use it only in trusted directories. It is not a security sandbox. Tools and model calls can have real effects and costs.

Extensions are optional participants.

Repeatable --x key[=value] supplies flags to installed extensions; it does not install them. pi-link can be one such extension, but pi-dock has no dependency on it. Headless UI prompts do not behave like an interactive terminal.

07 QUICK REFERENCE

One mental model.
A few ways to use it.

Discover, create, work, observe, power off. These twelve commands follow the same identity and session. The examples are not live controls.

pi-dock models haiku

Discovers models available with configured credentials. Optional case-insensitive filter; shows context, maximum output, thinking and image support.

pi-dock spawn --name atlas

Creates in the current directory, without a prompt. Options: --model provider/id, --thinking, repeatable --x. Extensions may start work of their own.

pi-dock send atlas --wait "Review this project"

Wakes if needed. Normally prints the accepted ID; --wait puts the ID on stderr and final-turn text on stdout. Use --file path instead of inline text.

pi-dock wait atlas p4a31b6c902ef

Reattaches to a run's outcome, including one already finished. Never resends the prompt or wakes the runner.

pi-dock start atlas

Powers on without sending a prompt. If it already responds, reports its state and model.

pi-dock stop atlas

Aborts and powers off; waits for process exit. Keeps configuration, log and memory, not queued work.

pi-dock ls

Lists name, derived state, stored model and age since creation.

pi-dock show atlas

Shows state and stored configuration: model, thinking, flags, working directory, session path and creation time.

pi-dock logs atlas --tail 5 --follow

Human-readable events and text by default; --raw gives NDJSON. --tail limits initial history; --follow continues until interrupted.

pi-dock set atlas --thinking high

Powered off only. Changes model, thinking or extension flags for the next wake. --x replaces the entire flag list.

pi-dock compact atlas "Keep decisions"

Wakes if needed; rejects active or queued work. Summarizes context with the model, waits for the result and leaves the runner on.

pi-dock skill

Prints the packaged operating guide for AI agents. Read it before operating the dock; use --help for the short command surface.

Portable names, explicit models.

Lowercase names, up to 64 characters; alphanumeric segments separated by ., _ or -. Windows reserved names are rejected. A model is resolved at creation; the stored provider/id is the authority on every wake. Preflight suggests available models when an unknown name has matches.

A timeout is not the same as being off.

set fails without mutating if the pipe does not respond. For a stuck runner, look up the PID of the last spawned, verify it still belongs to that agent before terminating it externally, then use start. Do not repeat commands blindly.
